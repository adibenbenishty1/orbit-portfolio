01Where each token comes from

The three-legged login — the only place both tokens are in the same building.

The browser never talks to gate and Auth0 in one breath; it is bounced between them by redirects. The exchange in steps 7–8 is the exception: that one is gate calling Auth0 directly, server to server, and it is the only moment an Auth0 token exists anywhere in orbit.

02Inside the exchange

One hop, two mints — the moment both tokens exist at once.

This is steps 7 through 9 of the diagram above, slowed down. It is the only back-channel call in the whole flow: no browser involved, gate calling Auth0 directly, authenticated with the client secret.

Two mints happen here, in this order.

Auth0 mints the id_token — at the moment it accepts the code, signed RS256 with a private key you never hold. It exists to answer one question: did this person authenticate?

Gate mints its own token — immediately after, from claims it read out of Auth0's. Signed HS256 with JWT_SECRET. It answers a different question: may this caller proceed?

Nothing is re-signed and nothing is converted. Auth0's token is read once, its useful fields copied out, and then dropped — never stored, never forwarded downstream, never shown to the caller.

What the minting extracts

Every field that crosses from one token to the other, and every one that doesn't.

Auth0's id_token says gate's token carries
sub→sub — verbatim, e.g. auth0|abc123
name→name — or sub, when absent
email→email — or null for a non-human caller
groups — raw, orbit-catalog-read→groups — normalised, catalog:read
iss · aud · nonce · at_hash✕dropped — provider bookkeeping
iat · exp✕dropped, then stamped fresh by gate
its RS256 signature✕replaced by an HS256 one

Four fields cross, and one of them is rewritten on the way. Everything else is left behind — including the timestamps, because gate's token has its own lifetime (JWT_TTL_HOURS, 24 by default) that has nothing to do with how long Auth0's assertion was good for.

03Where the groups come from

A directory role becomes an HTTP header — and changes vocabulary exactly once on the way.

The four crossing claims in the table above are not equals. Three of them say who, and Auth0 knows them because somebody typed a password. The fourth says what they may do — and Auth0 does not know that by default. Nothing in the act of logging in tells a provider that this person may read catalog. The fact has to be put into the tenant deliberately and then carried out of it deliberately, which is why groups costs four pieces of configuration while email costs none.

It travels inside the token for the reason the next section is about: /auth/check runs on every single request. Looking groups up from Auth0 per request would put a network hop, someone else's outage and someone else's rate limit into the hot path of the entire system. So the facts an authorisation decision will need are frozen into the credential at login, and carried by it from then on.

Step 4 is the one that is easy to mistake for plumbing. orbit-catalog-read is a name in someone else's directory, chosen to be unique across an organisation; catalog:read is a service and a role, which is the shape §6's policy layer will compare against. The orbit- prefix is an allowlist rather than decoration — a group without it belongs to some other part of the directory and is dropped, so a person's unrelated memberships can never widen what they may do here. A prefixed group whose tail is not read, write or admin is dropped too, which keeps the vocabulary total: every entry the policy layer ever sees is well formed.

What running the token through /check proved

Both halves had been proved separately and neither proof said they agree. The callback tests assert that a mint happens; the check tests assert that a hand-made token is accepted. Both can pass while the two ends disagree about what a group is called — and that disagreement would surface not as a failure but as a caller who authenticates perfectly and is quietly authorised for nothing.

So the token that came out of a real login was fed back into /auth/check, and the answer was X-Groups: catalog:read,catalog:write. That single header is the end of the chain: it is what nginx copies onto the forwarded request and what catalog reads instead of ever parsing a token. Getting it back means the role in the directory, the claim name in the Action, the prefix in the config and the vocabulary in the policy layer all agree — which is six pieces of configuration in three different systems, confirmed by one line of output.

  • Silent An Action that writes the claim to the access token only. gate reads the id_token and makes no userinfo call, so the claim is simply absent — the login succeeds, the token mints, and groups is [].
  • Silent A GROUPS_CLAIM that does not match the Action's string byte for byte. Same outcome, same absence of any error, and the claim name cannot be plain groups — Auth0 restricts that spelling, so it is always a namespaced URI that has to agree in two places.
  • Silent Editing .env under a running server. Config is read once at import, so the old value stays live and the symptom is indistinguishable from an Action that never fired.

All three end at an empty group list and a 200. None of them can be caught by a test that supplies its own claims, and none of them is visible without walking the whole chain against a real tenant — which is what the run above was for.

04Where the token goes

Every request after login — and Auth0 is not in it.

This is the loop that runs on every single request, and it is worth noticing what is missing from it. There is no call to Auth0, no JWKS fetch, no network hop outside the cluster. gate verifies a signature it made itself, with a key it already holds, and answers in microseconds.

05Two producers, one consumer

Why the CLI path is not a shortcut, a stub, or scaffolding to delete.

gate token mint -s ada produces a token that is byte-for-byte the same kind of thing the callback will produce: same key, same algorithm, same claim set. Nothing downstream can tell them apart, and nothing downstream should be able to. That is the whole reason gate issues its own token rather than passing Auth0's through.

06What the separation costs and buys

Four things that follow directly from the two tokens never touching.

  • Buys Swapping Auth0 for Okta, or for anything else, changes /auth/callback and nothing beyond it. No downstream service has ever seen a provider token, so none can depend on its shape.
  • Costs Auth0 has no idea gate's tokens exist. Delete a user or force a logout there and an already-issued gate token stays valid until exp. That gap is exactly what §3's revocation set in Redis is for.
  • Costs JWT_SECRET is the entire root of trust — anyone holding it can mint any identity with any groups. Every replica must share it, and two replicas with different keys produce intermittent 401s that look like anything but a config problem.
  • Watch Whether the id_token gets verified against Auth0's JWKS is still open — but wherever it lands, that check belongs in the callback. decode() should keep meaning one thing: is this a token gate itself signed.

Current state. The whole of figure 1 runs today against a real tenant, groups included — a login ends with a token gate signed, carrying catalog:read and catalog:write, and /auth/check answers 200 with both in X-Groups. What the callback still does not do is put the caller anywhere: it answers with the token as JSON rather than setting a session cookie and redirecting to the rd that came back on state. That ending is the next piece of work, and until it lands the browser leg stops one step short of the page the person actually asked for.
